**Part 1: completeness**

1. **present: isolated working copy and immutable export.** The chain owns separate base and working documents; exports carry immutable bytes and a revision ID. Evidence: `src/pdf/staged_revisions.cpp:138`, `:455`; `PdfStagedRevisions.BasePrefixPreserved`. This establishes byte preservation, not permission to make arbitrary changes to a certified PDF.

2. **present: basic edit history, branching and state identity.** Replacement/allocation, undo, redo, discarded redo branches and stale-change rejection have coverage in `MergeOrder`, `PushPopRedo`, `StaleChangeSet` and `RevisionIds`, starting at `tests/recto-tests/pdf_staged_revisions_tests.cpp:110`. Creation and deletion by actual editing tools still need the integration described below.

3. **present: long-history compaction and supported input representations.** `ManyEdits`, `NearLimitBases`, `SquashEquivalent` and `CompressedAndEncrypted` cover repeated edits, compaction, exact current-state export, xref streams and encrypted content. Evidence: `tests/recto-tests/pdf_staged_revisions_tests.cpp:247`. These tests do not cover the cumulative-object failure below.

4. **missing-in-scope: allocation failure must return an error rather than terminate Recto.** [`append_bytes`](/R:/GitHub/Recto/src/pdf/staged_revisions.cpp:261) is `noexcept`, but line 266 copies an owning `PdfValue` without a local exception handler. A string, dictionary or stream copy can throw `std::bad_alloc`; crossing this boundary calls `std::terminate` before the caller’s catch executes. Ordinary memory pressure during an edit, compaction or Save can therefore lose all unsaved work. Add allocation-failure coverage at this copy, requiring `OutOfMemory`, unchanged state and successful retry. The serializer/reopen injections in `TransitionsAreAtomic` do not exercise it.

5. **missing-in-scope: every accepted state must remain exportable within the declared limits.** [`merged`](/R:/GitHub/Recto/src/pdf/staged_revisions.cpp:235) applies the **100,000 objects per change set** ceiling to the union of the entire history. Two individually valid pushes allocating 60,000 small objects each can succeed within the history budget, while `export_squashed()` then refuses their 120,000-object union. Batch editing a large document can thus succeed visibly and fail only on Save or compaction. Keep the per-edit ceiling distinct from aggregate export bounds; test more than 100,000 distinct objects across accepted edits, including undo, redo and compaction.

6. **missing-in-scope: enforce retained-history bounds on every transition.** [`undo`](/R:/GitHub/Recto/src/pdf/staged_revisions.cpp:398) and [`redo`](/R:/GitHub/Recto/src/pdf/staged_revisions.cpp:435) publish their candidates without checking the resulting retained-byte total. Rebuilding an earlier, larger state after compaction can increase working bytes while retaining later change sets for redo. `drop_stale_revisions()` recounts after publication but cannot refuse. Validate candidate totals before publication and test histories near the ceiling with substantially different state sizes. Also preflight aggregate merges before copying their entries: `ObjectChangeSet::merge` and `merged` currently check their object limit after constructing the union.

7. **present: baseline refusal and atomicity tests, with the gaps above.** `FailedPushKeepsState`, `Bounds` and `TransitionsAreAtomic` cover invalid serialized values, prescribed ceilings and injected writer/reopen failures. Evidence: `tests/recto-tests/pdf_staged_revisions_tests.cpp:187`, `:404`, `:512`. Their presence is source evidence, not an independently verified passing gate.

8. **missing-out-of-scope: actor and editing-tool integration.** A user action must produce one intentional undo unit, publish the updated view, invalidate stale rendering, update dirty state and reverse create/change/delete operations. No engine work may block the UI thread. Owners: **D01 T02 §14**, domain **03** for markup/forms and domain **05** for Organize/redaction. Require end-to-end edit → undo → redo → Save → reopen tests. Redaction must use the secure final-write path: a prefix-preserving incremental export retains original content and cannot itself constitute sanitization.

**Part 2: excellence**

**Competitor baseline:** Acrobat Pro documents [Undo/Redo for text edits](https://helpx.adobe.com/acrobat/desktop/edit-documents/edit-text-in-pdfs/format-text.html) and [temporary autosave recovery](https://helpx.adobe.com/ca/acrobat/using/saving-pdfs.html). Foxit provides the strongest verified history-depth benchmark here: [10,000 actions, one toolbar click or one keyboard chord per undo/redo](https://www.foxit.com/resource-hub/user-guide/foxit-pdf-editor-for-windows/undo-and-redo/). PDFelement documents [Ctrl+Z/Ctrl+Y](https://pdf.wondershare.com/guide/shortcut-keys.html); UPDF documents [Undo/Redo menu access on Mac](https://updf.com/updf-mac-user-guide/toolbar-navigation-updf-mac/). I have no measured vendor latency, crash-test or accessibility results, so I cannot substantiate superiority on those dimensions.

1. **in-scope: reliable editing and Save are not established.** The termination, cumulative-export and transition-budget defects in Part 1 prevent a credible reliability advantage. **Target:** zero process termination under injected allocation failures; every accepted state exports and strictly reopens; every transition stays within its declared budget or fails atomically.

2. **in-scope: large-file latency has no demonstrated advantage.** Even an ordinary undo copies the remaining file bytes at `src/pdf/staged_revisions.cpp:412`, then reopens them; redo similarly copies the buffer. Small edits therefore incur work proportional to document size. **Target:** benchmark push/undo/redo/export at several file sizes and compaction boundaries, recording p50/p95 latency and peak memory; beat the fastest measured competitor on the same corpus and hardware. A proposed common-edit target is p95 below 100 ms. No current timing proves this.

3. **out-of-scope: history depth is one tenth of Foxit’s documented capacity.** `src/pdf/staged_revisions.h:31` fixes the cap at 1,000; push 1,001 is refused. **Target:** support more than 10,000 small reversible edits without forced Save, while preserving bounded memory and original-file protection. Domain **01** needs a follow-on design because this changes §13’s explicit limit; simply removing its safety bound is unacceptable.

4. **out-of-scope: no delivered crash-recovery advantage over Acrobat.** Saving the original from modification does not save the user’s unsaved work from a crash. **Target:** deliver the existing five-minute, encrypted-by-default recovery contract, demonstrate restoration after forced termination and prove failed snapshots never replace a good checkpoint. Owner: **D02 T01 §12**. This establishes a baseline; a stronger comparative claim needs measurements.

5. **out-of-scope: steps, accessibility and feedback remain undelivered.** Foxit’s common operation takes one click or one chord; this candidate has no user command path to count. **Target:** one chord or one toolbar click, zero confirmation dialogs for ordinary undo/redo, searchable Ctrl+K commands, named controls and clear disabled reasons. Long operations need prompt feedback and tested cancellation. Owners: domains **02/03/05**, with domain **01** cancellation support. Match the existing SPEC; use a board only for proposed surface changes. No visual or screen-reader superiority is established yet.

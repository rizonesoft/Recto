## adversarial: needs-attention

1. **P1: Debug builds can terminate on allocation failure.** `src/pdf/object.cpp:697` constructs a temporary `std::string` inside `noexcept` heap accounting. With MSVC checked iterators, that construction allocates a proxy; if Windows runs out of memory at that allocation while Recto resolves an indirect dictionary, the process terminates instead of returning `OutOfMemory`. To reproduce in a non-ASan x64 Debug build, inject failure into that proxy allocation during `PdfValue::heap_bytes()`. The allocation test at `tests/recto-tests/pdf_document_tests.cpp:1030` excludes allocations below 32 bytes, so it cannot catch this path.

2. **P2: Crafted object numbers cause excessive admission-table probing.** `src/pdf/document.cpp:1682` uses a fixed, public hash and linear probing without a work limit. Create a PDF whose outline nodes use generation-zero object numbers satisfying `splitmix64(number << 16) & 16383 == 0`, with a sparse cross-reference stream, then open it. An in-memory check found 8,192 such numbers through 134,663,124; inserting them into one generation requires about 33.6 million current-table probes. Longer page trees can repeat the collision pattern across generations.

3. **P2: The 64 MiB limit omits retained hash-table capacity.** `src/pdf/document.cpp:1658` assigns bucket overhead to individual entries, but eviction at `src/pdf/document.cpp:1719` subtracts those charges while `slots_` retains its peak bucket allocation. A document with many pages using distinct indirect `/Rotate` values can grow the map, after which navigating pages with large shared font descendants can evict the small entries and fill the reported budget. The retained buckets remain allocated while `bytes()` reports at most 64 MiB, so actual cache-owned heap can exceed the limit. `ObjectCacheBudget` measures large entries without first growing and emptying the map.

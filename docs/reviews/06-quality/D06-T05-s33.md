# D06 T05 §33: DCT /ColorTransform and Adobe APP14 CMYK and YCCK decoding

- **Section:** `D06 T05 §33` (`todo/06-quality/TODO-05-stamp-audits.md`), raised by the audit of `D01 T01 §8`
- **Candidate:** the commit that builds it (after `e82c847`)

## Self-review (implementing session, before the completion review)

- The transform a DCT image's samples went through is read as ISO 32000-1 Table 13 defines it: an Adobe APP14 marker's transform when present, else `/ColorTransform` (default 1 for three components, 0 otherwise). WIC's own behaviour was measured on the four fixtures (Windows PowerShell 5.1's WPF imaging, the same WIC JPEG codec): it converts three-component JPEGs without an Adobe transform of 0, and complements every four-component JPEG (converting Adobe YCCK first). The decoder now reads that back to the stream's own samples: raw three-component planes through `IWICPlanarBitmapSourceTransform` when `/ColorTransform 0` asks for them, CMYK complemented back, and YCCK declared only by `/ColorTransform` converted by Recto.
- The CMYK complement is a behaviour change worth naming: before it, Recto returned WIC's complemented values, so an Adobe CMYK image with the usual `/Decode [1 0 1 0 1 0 1 0]` was inverted twice. The samples are now as stored and `/Decode` (already passed to the decoder from the image dictionary) does the inversion, as in libjpeg, pdf.js and MuPDF.
- `PdfFilters.DctColorTransformAndAdobeCmykYcck` asserts each fixture block's exact or rounded colour (values checked with libjpeg through Pillow) and fails with the change disabled (no planar read, no complement). Existing DCT tests pass unchanged.

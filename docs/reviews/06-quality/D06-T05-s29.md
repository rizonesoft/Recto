# Review findings: D06 T05 §29 Damaged-file recovery resolves indirect object-stream parameters

- Candidate: the implementation commit named in the first round below, on top of `17bb0f4`.
- Implementer: Claude (Opus 5.5), attended campaign run 2026-10-23.

## Self-review (implementing session, before the completion review)

- Failure modes named for this area (`AGENTS.md`): unbounded recursion or allocation on hostile input, a malformed-input failure reported as success, and an engine function that throws. Recovery's resolver resolves one level and never recurses: a reference to anything but an uncompressed object the scan found, or to an object that does not parse, is null (ISO 32000-1 7.3.10). Every parse it does is charged to the scan's cumulative parse budget, every decode to the cumulative decoded `/ObjStm` budget, and an over-budget resolver aborts recovery with the budget error rather than being read as a damaged container. Deferred containers are held as the parsed stream (at most the file's size in total).
- Plan correction (recorded in the section): only containers whose parameters need resolving are deferred; deferring every container would lose the integers they hold for a later stream's indirect `/Length`. File order holds through `defined_at`, and catalog candidates carry their file position, so the root fallback still prefers the latest catalog in the file wherever its container was unpacked.
- Tests that fail before the change: `PdfXref.RecoveryResolvesIndirectObjStmParameters` (recovery could not locate the compressed catalog on `17bb0f4`); its catalog-order case fails when the position sort is removed (root 3 instead of 7); `RecoveryChargesFailedObjStmDecodes` adds the same budget case for deferred containers.
- Architecture check: the change stays inside `XrefTable::recover_damaged_xref`; no thread contract, module seam or data ownership changes.

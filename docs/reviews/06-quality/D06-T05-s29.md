## Self-review (implementing session, before the completion review)

- Failure modes named for this area (`AGENTS.md`): unbounded recursion or allocation on hostile input, a malformed-input failure reported as success, and an engine function that throws. Recovery's resolver resolves one level and never recurses: a reference to anything but an uncompressed object the scan found, or to an object that does not parse, is null (ISO 32000-1 7.3.10). Every parse it does is charged to the scan's cumulative parse budget, every decode to the cumulative decoded `/ObjStm` budget, and an over-budget resolver aborts recovery with the budget error rather than being read as a damaged container. Deferred containers are held as the parsed stream (at most the file's size in total).
- Plan correction (recorded in the section): only containers whose parameters need resolving are deferred; deferring every container would lose the integers they hold for a later stream's indirect `/Length`. File order holds through `defined_at`, and catalog candidates carry their file position, so the root fallback still prefers the latest catalog in the file wherever its container was unpacked.
- Tests that fail before the change: `PdfXref.RecoveryResolvesIndirectObjStmParameters` (recovery could not locate the compressed catalog on `17bb0f4`); its catalog-order case fails when the position sort is removed (root 3 instead of 7); `RecoveryChargesFailedObjStmDecodes` adds the same budget case for deferred containers.
- Architecture check: the change stays inside `XrefTable::recover_damaged_xref`; no thread contract, module seam or data ownership changes.

**Part 1: completeness**

1. **present: automatic recovery when cross-reference data is damaged.** `Document` enables recovery at `src/pdf/document.cpp:1300`; fallback is implemented at `src/pdf/xref.cpp:1377`. `PdfXref.DamagedRecovery` checks strict rejection and successful recovery. `PdfDocument.BrokenCorpusSweep` verifies that an existing damaged fixture opens with one page and readable content (`tests/recto-tests/pdf_document_tests.cpp:2140`).

2. **present: forward references for `/DecodeParms`, `/N` and `/First`.** Deferred containers resolve parameters after scanning (`src/pdf/xref.cpp:1152`, `1266`, `1275`). `PdfXref.RecoveryResolvesIndirectObjStmParameters` covers these cases, including parameter objects after the container (`tests/recto-tests/pdf_xref_tests.cpp:210`).

3. **missing-in-scope: regression coverage for the full advertised parameter surface and usable document.** The new test always uses a direct `/Filter /ASCIIHexDecode`, an empty parameter dictionary and an empty page tree. It never resolves the recovered catalog or opens a document. Add recovery cases for indirect `/Filter`, referenced filter-array elements, parameter arrays and their referenced values, plus a nonempty document opened through `Document::open_memory`. Verify page count and decoded content. Generic filter tests do not exercise recovery’s separate filter precheck (`src/pdf/xref.cpp:1228`; `tests/recto-tests/pdf_xref_tests.cpp:210`).

4. **present: object-definition and catalog precedence.** `defined_at` prevents an earlier deferred member replacing a later definition (`src/pdf/xref.cpp:806`); redefined containers are skipped (`1223`). Catalog fallback uses file position (`1326`). The new regression tests cover compressed/uncompressed precedence and both catalog orders.

5. **missing-in-scope: metadata fallback loses file order.** Without a surviving trailer, an earlier deferred container containing metadata object 6 can replace a later uncompressed metadata object 8 as `/Info`. The scan selects object 8 at `src/pdf/xref.cpp:1087`; deferred unpacking subsequently assigns object 6 at `877`; fallback publishes it at `1337`. Unlike catalog selection, metadata selection carries no position. Add both ordering directions and assert the selected `/Info` and title. This violates the section’s requirement to preserve file order.

6. **present: bounded, nonrecursive parameter lookup.** Missing objects, wrong generations and unavailable compressed targets become null; the resolver never follows reference chains (`src/pdf/xref.cpp:1157`). Invalid resolved counts cause the container to contribute no members (`730`). If no valid catalog remains, recovery returns `DamagedFormat` with `DamagedXRef` (`1346`). Existing `PdfXref.DamagedRecovery` cases cover invalid roots, aliases and redefinitions, although not these new deferred-reference combinations.

7. **present: parsing and object-count budgets.** Recovery caps candidate attempts and discovered entries, and limits cumulative parsing to `max(file_size * 4, 65536)` (`src/pdf/xref.cpp:645`, `668`, `795`, `974`, `1177`). Exceeding these recovery budgets returns `DamagedFormat`/`DamagedXRef`. Parser nesting is capped at 64, with value and byte ceilings (`src/pdf/parser.h:25`). Evidence includes `PdfXref.DamagedRecovery`, `PdfParser.RecursionLimit`, `TotalValueBudgetSpansContainers` and `TotalByteBudgetSpansValues`.

8. **present: bounded decoding, including unsuccessful work.** The deferred path preserves the 256 MiB stream ceiling and cumulative object-stream budget, charging failed decodes too (`src/pdf/xref.cpp:1274`; `src/pdf/filters.h:21`). Exhaustion returns `DecompressionLimitExceeded`; unmetered filters are skipped with a damage diagnostic (`src/pdf/xref.cpp:1261`). `PdfXref.RecoveryChargesFailedObjStmDecodes` includes deferred containers (`tests/recto-tests/pdf_xref_tests.cpp:307`).

9. **missing-in-scope: adversarial regression tests for the deferred path.** No added recovery test exercises missing, wrong-generation, cyclic or wrong-type parameter targets; invalid indirect counts; deferred resolver parse-budget exhaustion; or malformed deferred headers with an independent surviving catalog. Assert the intended skip or exact typed refusal, retained valid objects and diagnostics. Existing direct-container tests cannot detect regressions confined to the new resolver.

10. **missing-in-scope: shared parameter objects can cause unnecessary refusal.** Every lookup reparses its entire target (`src/pdf/xref.cpp:1164`) and charges it again (`1177`), without reuse. Four containers sharing one approximately 16 KiB `/DecodeParms` dictionary can cause five dictionary parses, including the original scan, exceeding the four-times-file budget when that dictionary dominates the file. This is a source-derived failure case, not an executed reproduction. Add a regression proving this benign shared-reference file recovers while genuinely excessive work still returns `DamagedFormat`.

11. **present: malformed-member isolation and typed terminal failures.** Invalid member syntax is rejected by `extract_object_stream_member`; recovery skips it and retains other members (`src/pdf/xref.cpp:811`, `2148`). Missing catalogs return `DamagedFormat`; allocation failure returns `OutOfMemory`; unexpected exceptions at the recovery boundary return `InternalError` (`1346`, `1355`). `PdfXref.DamagedRecovery` tests rejected members and surviving catalogs. Empty/non-PDF inputs return `NotAPdf`; truncated headers return `DamagedFormat`, covered by `PdfXref.RejectsBrokenFiles`.

12. **present: original preservation and basic support diagnostics.** Recovery accepts immutable bytes (`src/pdf/xref.h:206`), and disk opening uses `GENERIC_READ` (`src/pdf/document.cpp:1092`). Recovery records `DamagedXRef` and exposes a recovered flag. The diagnostic ring contains codes, offsets and object identifiers, without document payloads (`src/pdf/error.h:1074`). `PdfXref.DamagedRecovery`, `PdfDocument.BrokenCorpusSweep` and `PdfError.DiagnosticRingWraparound` cover these basic signals.

13. **missing-out-of-scope: encrypted compressed-catalog recovery.** At this candidate, recovery attempts object-stream decoding before authentication; the security handler is initialized only after xref parsing succeeds (`src/pdf/document.cpp:1298`). The scanner copies a surviving xref stream’s trailer fields but does not retain its compressed-object rows (`src/pdf/xref.cpp:1093`). Consequently, an encrypted file whose only catalog is compressed can fail before password handling. Encrypted object streams require decryption before their contents can be interpreted. Owner: **01-engine**, covering preserved type-2 rows, authentication and typed password/encryption failures. Add damaged RC4/AES fixtures with correct, wrong and absent passwords. [ISO 32000-1, §7.5.7](https://opensource.adobe.com/dc-acrobat-sdk-docs/standards/pdfstandards/pdf/PDF32000_2008.pdf).

14. **missing-out-of-scope: other recoverable reference layouts.** Recovery recognizes only direct `/Type /ObjStm` and its parameter resolver excludes compressed targets (`src/pdf/xref.cpp:1098`, `1159`). An indirect container `/Type`, or a parameter stored in another independently recoverable object stream, remains unsupported. Owner: **01-engine**, as a bounded dependency-resolution section with corresponding fixtures. The current section explicitly limits its resolver to uncompressed objects.

15. **missing-out-of-scope: a document-specific recovery result that distinguishes partial success.** The delivered result offers a recovered boolean and a process-wide, 256-entry diagnostic tail. Invalid `/N`, `/First` and header checks can simply discard a container without recording its specific rejection (`src/pdf/xref.cpp:730`, `747`, `883`). Support cannot reliably determine which objects were skipped, why, or whether losses are known. Owner: **01-engine**. Add a bounded recovery report with rejection reasons, object identifiers, budget outcomes and explicit unknowns; test partial recovery and diagnostic-ring overflow.

16. **missing-out-of-scope: user-facing success, partial-success and failure handling.** No candidate app consumer presents the recovered flag or partial-loss information. The failure dialog and privacy-safe diagnostic copy are planned in `D02 T01 §11`, but remain unchecked (`todo/02-viewer/TODO-01-app-shell.md:405`). Owner: **02-viewer**, with an engine-report dependency and a SPEC subsection for the new recovery-success surface. Verify recovery notices, actionable refusal categories, accessible announcements and copied support details.

17. **missing-out-of-scope: cancellation and progress during large recovery.** `recover_damaged_xref` has no cancellation or progress interface (`src/pdf/xref.h:206`). Byte budgets bound work but do not let someone cancel an expensive open. Owner: **01-engine**, consumed by **02-viewer**. Test cancellation during scanning, parameter resolution and decoding, with `Cancelled` returned and no surviving partial session.

18. **missing-out-of-scope: salvage beyond rebuilding the index, and durable recovery output.** Finding a catalog does not establish that the page tree and surviving content are usable. Document loading can subsequently fail, and this feature provides no page-salvage or repaired-copy workflow. Owners: **01-engine** for bounded salvage and writing, **02-viewer** for preview and Save a copy. Test damaged page trees, retained pages/content, successful reopening of the saved copy, atomic-write failure and byte-for-byte preservation of the original.

**Part 2: excellence**

**Competitor: Adobe Acrobat Pro is the primary benchmark.** Adobe documents repair during opening through `PDDocOpen(..., doRepair=true)`, distinct password and rebuild-failure outcomes, a repaired-document flag, document-specific nonfatal errors and saving. These establish a recovery workflow, but do not establish that Acrobat recovers this candidate’s exact fixtures. No same-file results establish which of Acrobat, Foxit, PDFelement or UPDF is strongest here. [Adobe Acrobat SDK](https://opensource.adobe.com/dc-acrobat-sdk-docs/acrobatsdk/apireference/PD_Layer/PDDoc.html).

1. **in-scope: no demonstrated recovery advantage on the delivered file class.** The evidence is synthetic xref assertions, without matched competitor outcomes or a usable-document assertion for the new cases. **Target:** recover every intact, within-budget indirect-parameter fixture through document opening; record exact competitor versions and outcomes on identical files; demonstrate at least one additional safely recovered case or another measured advantage.

2. **in-scope: avoidable work undermines large-file recovery.** Shared targets are reparsed, and catalog selection now sorts candidates (`src/pdf/xref.cpp:1327`) rather than requiring only a linear selection. No timing establishes an advantage. **Target:** shared-parameter recovery without artificial budget exhaustion; linear catalog selection; publish median, p95 and peak memory for a fixed large damaged corpus. A proposed winning threshold is p95 recovery time at most 80% of the strongest measured competitor, without reducing content retention or existing safeguards.

3. **in-scope: surviving information can be older than the recovered file’s latest definition.** The `/Info` regression in Part 1 item 5 directly weakens retention. **Target:** latest metadata selected in both storage orders; for xref-only damage, page content and metadata match the undamaged control, with regression tests.

4. **out-of-scope: the recoverable-file envelope excludes protected and other referenced layouts.** The encrypted compressed-catalog and compressed-parameter gaps prevent a broad recovery claim. **Target:** recover supported, authenticated RC4/AES cases and acyclic cross-container parameter layouts within unchanged limits; distinguish password, unsupported-encryption, damage and budget refusals. Owner: **01-engine**.

5. **out-of-scope: recovery does not yet tell the user what survived or provide a durable result.** A recovered flag is insufficient to beat a mature repair-and-save workflow. **Target:** one clear recovery notice; known losses and unknown completeness stated accurately; document-specific support details; a repaired-copy action whose output reopens and whose original remains unchanged. Owners: **01-engine** and **02-viewer**.

6. **out-of-scope: expensive recovery cannot be cancelled through the engine API.** **Target:** cancellation acknowledged within 100 ms on the reference host during each recovery stage, while retaining Recto’s existing UI responsiveness requirements. Owners: **01-engine** and **02-viewer**.

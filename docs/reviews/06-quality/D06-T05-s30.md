## Self-review (implementing session, before the completion review)

- Failure modes named for this area (`AGENTS.md`): unbounded allocation on hostile input and a malformed-input failure reported as success. Recovery decodes each intact `/Type /XRef` stream once, charged to the same cumulative decoded budget as containers, and imports its rows through `unpack_xref_stream`, whose entry budget is the recovery's; every row counts against the object entry budget.
- Encrypted containers are never decoded during recovery: a file naming `/Encrypt` defers every container, and none is decoded once a recovered trailer has `/Encrypt`; their members come from the xref stream's type-2 rows and are read after authentication by the normal path (`SecurityHandler`, `parse_object_stream`, `extract_object_stream_member`). A file that merely mentions `/Encrypt` has its containers decoded after the scan, as `§29` does.
- Rows name a container by number, not by one version of it, so they are kept out of `objstm_members`: the container's own definition does not invalidate them. A row is a definition at its stream's position under the later-wins rule (`defined_at`).
- A trailer `/Root` naming a compressed object is accepted only in an encrypted file, where its container cannot be read before authentication; resolution checks it after authentication.
- Plan correction (recorded in the section): a single forward scan cannot know about `/Encrypt` before it meets the containers, hence the byte search and deferral.
- Test that fails before the change: `PdfDocument.RecoveredEncryptedObjectStreamsResolve` (object 21 is missing after recovery on `5f438c0`). The shared fixture moved into `encrypted_objstm_update`, used by it and by `EncryptedObjectStreamsShareOneDecodeAndRefuseForbiddenMembers`.
- Architecture check: the change stays inside damaged-file recovery and the existing authentication order (`Document` opens, recovers, then authenticates); no thread contract or module seam changes.

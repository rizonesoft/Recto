# Review findings: D06 T05 §37 WIC decode failures classified by HRESULT, not reported as damage

- Candidate: the implementation commit named below.
- Implementer: Claude (Opus 5.5), attended campaign run 2026-10-23.

## Self-review (implementing session, before the completion review)

- Failure modes named for this area (`AGENTS.md`): a malformed-input failure reported as success, and a failure misreported. Every failed WIC call in DCTDecode (twelve sites) returns through `wic_failure`, which reads the HRESULT: `E_OUTOFMEMORY` is `OutOfMemory`, `WINCODEC_ERR_COMPONENTNOTFOUND` and `WINCODEC_ERR_UNSUPPORTEDPIXELFORMAT` are `UnsupportedFeature`, `E_ABORT` is `Cancelled`, anything else is `DamagedFormat`, each with the HRESULT in hex in the message. A call that succeeds without its result (no decoder, a zero size) stays `DamagedFormat`.
- JPXDecode's WIC attempt is one function returning an image, a ceiling refusal, or the HRESULT that stopped it; only a codec or data failure hands the stream to the native decoder, and a resource failure (`E_OUTOFMEMORY`, `E_ABORT`) is returned without a native attempt.
- `detail::ScopedWicDecoderFailure` injects an HRESULT at `CreateDecoderFromStream` (the one call both paths share) for tests only; it is thread-local and scoped like `ScopedJpxPath`.
- `PdfFilters.WicFailureClasses` covers each class for DCT and both JPX outcomes. Mutants: every HRESULT read as damage fails it (`OutOfMemory` and `Cancelled` cases), and a resource failure falling back fails it (`img.has_value()`).
- Decision taken (default, cost of reversing): the classes are exactly the section's list; another HRESULT that means "absent codec" (for example `WINCODEC_ERR_UNSUPPORTEDOPERATION`) reads as damage until a file shows it. Adding one is a `case` line and a test row.

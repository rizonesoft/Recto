# Review findings: D06 T05 §38 DCT decodes only the pixel representation the caller asked for

- Candidate: the implementation commit named below.
- Implementer: Claude (Opus 5.5), attended campaign run 2026-10-23.

## Self-review (implementing session, before the completion review)

- Failure modes named for this area (`AGENTS.md`): unbounded allocation on hostile input, and a stride or layout assumed. `decode_dct_image` takes a `DctOutput` (all three buffers, samples, RGBA, BGRA, or `Stream`, what DCTDecode returns as a filter) and builds only that; the samples are always decoded first and released afterwards when not asked for. The ceiling is charged with the peak of what is built (samples plus the 8-bit layouts asked for), so `Stream` on an RGB photo charges 3 bytes per pixel instead of 11.
- `decode_dct` asks for `Stream`, which reads a direct caller's `/TargetFormat` for a CMYK image exactly as before (RGBA by default, BGRA, or the CMYK samples); a stream dictionary's `/TargetFormat` is still dropped earlier (`PdfFilters.DocumentCannotSetTargetFormat` passes unchanged).
- `PdfFilters.DctLargePhotoWithinCeiling` encodes a 6000 x 4500 baseline JPEG with WIC's own encoder, decodes it through `decode_stream` at the default ceiling, and holds the heap meter's peak under one buffer plus 10 percent; with `decode_dct` asking for all three buffers it is refused (`DCTDecode cumulative decoded image buffers exceed ceiling`), as before this section.
- Decision taken (default, cost of reversing): `decode_dct_image` keeps `All` as its default, so existing direct callers and tests that read every buffer are unchanged; the stream filter is the path that asks for one. Reversing the default is a parameter change.

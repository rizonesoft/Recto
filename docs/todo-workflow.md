# TODO workflow

Link this file from the project's `AGENTS.md` (for example: "Plan and build through the TODO system in [docs/todo-workflow.md](./docs/todo-workflow.md).") so every agent reads it.

`todo/` is the live execution plan; format spec: `todo/README.md`. Markdown is canonical.

Core mechanics: the Implementation Order table in each TODO file is the dependency graph; a row flips to `[x]` only through `python scripts/todo-graph.py stamp`, backed by a review receipt in `docs/reviews/` that records the plan review (`--plan`), the completion review (`--completion`) and the rounds, each pass checked against the pinned review schedule; `todo/implementation-plan.md` is regenerated by `plan --sync`, never ticked or edited by hand; cross-references (`§N`, `TNN §N`, `DNN TNN §N`) are bidirectional; every section declares Phase, Needs and Surface, carries a Build order with `Done when:` per step, and must be implementable with zero conversation context.

Granularity and 100% plan completeness:
- **Small, single-responsibility sections:** Never bundle multiple subsystems, dialogs, or workflows into one coarse umbrella section. Split every TODO file into small, single-responsibility sections that each deliver one coherent, testable capability.
- **Short table descriptions (`<= 88` chars):** Keep section headings (`## N. <Title>`), `Deliverable` cells in `Implementation Order`, and `Scope` cells in index tables to a concise noun phrase of at most 88 characters so raw Markdown table rows stay under 140 characters (with description cells <= 88 characters) and never wrap in raw `.md` editors. Put file paths, symbols, CLI flags, and enumerations in the section body and micro-steps, never in the heading or table cell.
- **Granular micro-step checklist items:** Every section carries 1 to 30 buildable micro-step items (typically 4 to 15 concrete micro-steps, never a 1-bullet summary stub), ending with `- [ ] Commit: <message>`. Each non-Commit item names one action, a concrete path/symbol/command in backticks, an observable `Done when:` in the same bullet, a `Cheaper substitute:` on UI and write items, and a source citation when copying behavior from the plan or SPEC.
- **100% complete development plan:** Running `process-plan` to completion must produce a 100% complete, shippable product with zero unowned surfaces, controls, settings, refusal/error paths, undo/reverse paths, or persistence read-backs. Never cap operator-requested planning and never silently drop scope.

For TODO work, use the skill in `.claude/skills/` (shared with Google Antigravity through `.agents/skills.json`) that owns the step (Claude Code `claude` and Google Antigravity `agy` are the writers; GPT-6 Astra reviews every pass through `scripts/review-dispatch.py` on the `three-pass` schedule pinned in `.conclave/reviewers.toml`, which routes the writers `claude`, `agy` and `muse` to it alone): capture through `add-todo`, author a file through `create-todo`, build through `process-todo-section`, stamp through `review-todo-section`, close a file through `process-todo-file`, run a phase or the plan through `process-phase` or `process-plan`, harden the tree through `groom-plan`. The lifecycle under the `three-pass` pin is: capture, author, validate, the one-pass plan review (`--kind plan` filled via `scripts/review-prompt.py`, its gaps fixed in the section before any code), record `Started:`, implement with fast targeted local builds and tests (`.\build.cmd -Quick -Project <vcxproj> -TestFilter <filter>`, `python scripts/run-tests.py --quick`), run the section's Test checkpoint and touched gates, commit and push so GitHub Actions CI (`ci_status.py --wait`) runs the full x64/ARM64/ASan matrix in parallel with the single review round (`--kind round`), fix findings and re-run touched gates, run the one-pass completion and excellence review (`--kind completion`, plus `--kind reconciliation` if blocking gaps remain, or file `P3` gaps via `add-todo`), verify `ci_status.py --gate` is green, stamp, and sync the plan.

## Rules for TODO work

- **Tests prove claims:** a section's Test checkpoint must be able to fail, and is quoted, not paraphrased, in its stamp.
- **Balanced local-vs-CI cadence:** keep local loops fast by building touched projects and running targeted test filters plus `python scripts/run-tests.py --quick`; push candidate commits to `main` and run `ci_status.py --wait` in parallel with review so GitHub Actions shoulders the full matrix (`build.yml` x64/ARM64/ASan and `plan.yml` `--full`), reserving local full builds for phase closeouts or build/toolchain changes, and healing any red CI immediately at the owning layer.
- **Commits:** trunk-based `main`, concise imperative messages, the section ref in the body. Commits follow logical steps within a section; review fix-loop commits append to the candidate range. Never amend a candidate under review, never bypass hooks, never force-push.

## Validation

```bash
python3 scripts/todo-graph.py validate        # graph integrity; any fault exits 2 with the reason
python3 scripts/todo-graph.py plan --check    # generated plan is current (CI runs this)
python3 scripts/todo-graph.py query ready     # dependency-safe work right now
python3 scripts/todo-graph.py query blocked   # sections waiting, and on what
python3 scripts/todo-graph.py query stats     # tree health
python3 scripts/todo-graph.py query deferred  # open and resolved deferrals
python3 scripts/todo-graph.py query plan      # plan title, phase names and every section's status, as JSON
python3 scripts/todo-graph.py resolve 'D01 T02 §10' --context   # one section to build or review, read in place of its file
```

`resolve '<ref>' --context` prints, as Markdown and with `resolve`'s exit codes (0 ready, 1 no such section, 2 no reference or a refused graph, 3 verified, 4 waiting): the file's state and why the section waits, the file's own context (title, Goal, Current state, Inputs, Outcome, Adjacency, the Implementation Order table) and the section word for word, the file's Verification block, each prerequisite's effective state with its stamp and receipt, the section's waiting Needs, and every cross-reference and deferral that names the section or that it makes, with `path:line`. A session building or reviewing one section reads that output and does not open the TODO file; `process-todo-file` and `groom-plan` still read whole files.

# TODO system: format spec

The `todo/` tree is the live execution plan for building Recto to version 1. Markdown is canonical; `build/todo-cache.json` is a derived, gitignored projection. The one committed derived artefact is [`implementation-plan.md`](./implementation-plan.md), generated from the sections and never edited by hand.

One rule governs everything below: **a TODO section must be implementable by someone with zero conversation context.** A fresh session starts with none. If a section only makes sense to someone who was in the room, it is not done.

This system is the same one used in Derick's other repositories (ScratchPad, Resolute, swisshotelschool-coza, rizonetech-com), seeded here in its clean strict form: one validator that refuses malformed work, a generated plan, and stamps backed by review receipts. The governing product documents stay where they are: architecture and milestones in `docs/plans/2026-10-13-recto-foundation.md`, the interface in `design/SPEC.md`. TODO files execute those documents; they do not restate them.

## Tree shape

```
todo/
├── README.md               this file
├── TODO-00-INDEX.md        root index: domain order + active work
├── implementation-plan.md  generated by plan --sync; never edited by hand
├── findings.md             defects noticed while doing something else (file:line, unscheduled)
├── templates/              TODO-template.md (same file the create-todo skill carries)
├── 00-workspace/
│   ├── INDEX.md            domain index: every TODO in this domain
│   ├── TODO-01-<short-name>.md
│   └── TODO-02-<short-name>.md
├── 01-engine/
└── …
```

Domains are flat-numbered in allocation order and map to the foundation plan's milestones: `00-workspace` (M0), `01-engine` (M1), `02-viewer` (M2), `03-text` (M3), `04-convert` (M4 and M5), `05-organize` (M4), `06-quality` (cross-cutting), `07-release` (M6), `99-manual` (operator only). Numbers are stable addresses: a new domain appends after the last one, because `DNN` cross-references encode them. Execution order lives in the dependency graph, not in the numbering.

Naming: `TODO-NN-short-name.md`, where `NN` is the next free number within that domain. Numbers are never reused. Renaming a file is safe: the stable `id` in frontmatter is what file-level references resolve against.

## Frontmatter

Every TODO file opens with YAML frontmatter, one scalar per line with no inline `#` comments. Five required fields, four optional. That is the whole schema: resist adding more.

```yaml
---
schema_version: 1
id: bridge-runtime
domain: 01-engine
status: active
title: "TODO-01 -- Native PDF Parser, Filters, Crypto and Document Model"
depends_on: ["repo-and-build"]
frozen: true
track: M1
superseded_by: other-todo-id
---
```

`id` rules: lowercase `a-z0-9-`, 2 to 60 chars, starts with a letter, no trailing dash, globally unique, and survives renames. `domain` must match the containing directory. `status` is one of `draft`, `active`, `blocked`, `done`, or `superseded`: only `active` files produce ready sections, `done` is true exactly when every section is stamped (the last stamp sets it), and a `superseded` file must set `superseded_by` to name where its work went. Optional `depends_on` lists TODO `id`s that must fully ship first, `frozen: true` marks files touching the frozen thread-safety contract, and `track` names the milestone (`M0` to `M6`).

## File anatomy

In order: frontmatter, `# TODO-NN -- Title`, `> **Goal:**`, `> **Current state:**` (measured, dated, real paths), `## Inputs`, `## Outcome` (with the Adjacency line), `## Implementation Order`, the numbered sections `## 1.` to `## N.` in ascending order, and `## Verification` last. New sections go in numerical position, never after `## Verification`.

### The Implementation Order table is the dependency graph

Every `## N.` body section has exactly one row (`Order`, `§N`, `Deliverable`, `Depends On`, `[ ]`), and every row has exactly one body section. Both the `Deliverable` cell and the section title (the `<Title>` in `## N. <Title>`, without the `## N. ` prefix, which no table shows) must be at most 88 characters (`MAX_DELIVERABLE_LEN = 88`) so Markdown tables never wrap in the editor. The validator enforces both directions, refuses cycles, refuses a prerequisite in a later phase than its consumer, and refuses a ticked row without its stamp. A file holds at most 55 sections: past that, the next work opens a new file in the same domain, split by subject. Section numbers are permanent addresses and are never renumbered.

### Cross-reference notation

| Form | Means | Example |
| ---- | ----- | ------- |
| `§N` | Section N of this same file | `§3` |
| `TNN §N` | TODO-NN in the same domain, section N | `T02 §1` |
| `DNN TNN §N` | Domain NN, TODO-NN, section N | `D03 T01 §4` |

Never a bare number, and never a cross-TODO reference without a section. Cross-references in `-> XREF:` lines are bidirectional at file level: if this file points at `D03 T01 §4`, that TODO file must point back at a section in this file. The validator refuses one-sided XREFs and XREFs that name no real section.

### What every section declares

- `**Phase:**` from the closed list: 0 (M0 Repository and build), 1 (M1 Engine core), 2 (M2 Viewer), 3 (M3 Text), 4 (M4 Conversions A), 5 (M5 Conversions B), 6 (M6 Ship), 7 (After v1), 99 (Manual, operator only). The phase drives plan ordering; changing one is a scope decision.
- `**Needs:**` `none` or a comma-separated list from: `windows-host`, `arm64-host`, `display-session` (an interactive Windows session that can render WinUI), `office` (Microsoft Office installed), `libreoffice` (LibreOffice installed), `store-account`, `attended` (a human present while it runs), `owner-decision`, `third-party`, `operator` (operator-only work, domain 99). `owner-decision`, `third-party` and `operator` hold the section out of `query ready` until the answer is recorded and the Need is removed. Unattended runs never take an `attended`, `store-account` or `operator` section.
- `**Surface:**` `yes` or `no`. A `yes` section builds or changes a user-facing surface and also carries four lines: `**Fidelity:**` (the `design/SPEC.md` section and screenshot it must match; a genuinely new surface says so explicitly), `**Job:**` (the user, the verb, and what consumes the write), `**Treatment:**` (the asked treatment and the cheaper substitute that fails the checkpoint), `**Chrome:**` (the shared controls, slots and tokens it consumes; never a second pattern).
- `**Freeze check:**` in every section of a `frozen: true` file, and nowhere else. Recto's frozen contract is foundation plan section 4 (`recto-pdf` and `DocumentActor` thread safety): restructuring frozen code is allowed, changing what it guarantees requires a recorded operator approval in the section.
- `**Build order:**` numbered steps, each naming a path, class, command or artifact in backticks and an observable `Done when:`.
- A checklist of 1 to 30 micro-step items, `- [ ] Commit: <message>` last. One item is one buildable step: one action, a named path in backticks, a done-when, the cheaper substitute on UI and write items, and a source cite when behaviour is copied from the SPEC, the plan or the ISO 32000 PDF specification.
- `**Test checkpoint:**` a runnable command in backticks with its expected result. It must be able to fail.

Do not rewrite a `[x]` section's checklist: that is the contract its stamp covers. New granularity on shipped work is a new section.

### Adjacency: the surfaces a file owes beyond its record

`## Outcome` carries one executable `**Adjacency:**` line. Write every key exactly once, separated by semicolons: `key=applicable`, `key=applicable @ DNN TNN §N` for an explicit owner, or `key=not-applicable (reason)`. A narrow non-feature file may declare `all=not-applicable (reason)`. The nine keys: `list` (find a record without its identifier), `document` (what a user carries, sends, prints or files), `settings` (every tunable, with a named consumer), `reporting` (summaries and exports over the domain's data), `notifications` (lifecycle notices with recipient rules), `permissions` (refusals exercised, both ways), `audit` (who changed what, and the diagnostic trail), `exchange` (import and export), `reverse` (the undo of every create: cancel, reopen, revert). "Not applicable" is a declaration with a reason, not silence. Owner references must resolve; `python scripts/todo-graph.py query adjacency` prints every declaration. An `**Adjacency rationale:**` paragraph under the line records the substantive decisions for human review.

## Stamps and receipts

A section closes only through `stamp`:

```powershell
python scripts/todo-graph.py stamp 'D01 T01 §1' --sha <full 40-char implementation commit> --review '1:docs/reviews/01-engine/D01-T01-s1.md:clean' --check '<command> -> <quoted result>'
```

`stamp` refuses unless every checklist item except `Commit:` is ticked, every prerequisite is stamped, no waiting Need remains, the SHA is a full commit on this branch, at least one review round (`clean`, `fixed` or `stopped-at-22`; `stopped-at-13`, `stopped-at-8` or `stopped-at-3` on receipts from earlier caps; with the findings file as its report) and at least one check are given. A `stopped-at-22` verdict, or `stopped-low-severity` (from round 9 on, a round with only `P3` or advisory findings, declared by the reviewer as `HIGHEST: P3`, ends the loop and its findings are filed), also needs `--cap-outcome` saying what was done. The receipt records `rounds_spent` and `round_cap` (and `cap_outcome`); `query rounds` summarises them. It then writes the receipt `docs/reviews/<ref>.json`, ticks the `Commit:` item and the Implementation Order row, appends the stamp at the end of the section, marks the file `done` when its last section stamps, and refuses to leave a half-written record behind:

```markdown
> **Verified:** YYYY-MM-DD | §N | FULL_IMPLEMENTATION_SHA
> **Review:** `docs/reviews/<ref>.json`
```

Optional stamp companions, written by hand before stamping: `> **Started:** <UTC ISO instant>` under the section heading (written once, never overwritten on resume), `> **Deferred:** <what> -> XREF: DNN TNN §N` (one per deferral, each naming its concrete owner; a deferral without an owner is an abandonment, and the moment the owner ships, a still-open `Deferred:` refuses validation, so the section that resolves a deferral is the section that closes it by replacing the marker with `> **Resolved:**` in place, keeping the text and adding the date and what closed it).

A passing validator proves structure, not that the work was done. The receipt is the evidence: review rounds with their findings files, and checks with quoted results.

## Commands

```powershell
python scripts/todo-graph.py validate            # structure + graph integrity; exits 2 with the reason on any fault
python scripts/todo-graph.py build               # parse todo/ -> build/todo-cache.json
python scripts/todo-graph.py render              # mermaid dependency graph
python scripts/todo-graph.py plan --sync         # regenerate todo/implementation-plan.md after any edit
python scripts/todo-graph.py plan --check        # fail if the generated plan is stale (CI runs this)
python scripts/todo-graph.py query ready         # sections that can run now (also: blocked, stats, deferred, adjacency)
python scripts/todo-graph.py resolve 'D01 T01 §1'  # 0 ready, 1 no such section, 2 no reference, 3 verified, 4 waiting
python scripts/todo-graph.py classify 'D01 T01 §1' 'D02 T01 §1'   # dispositions as JSON
python scripts/todo-graph.py stamp 'D01 T01 §1' --sha <commit> --review '1:<report>:clean' --check '<cmd> -> <result>'
python -m unittest tests.scripts.test_todo_graph   # the tooling's own tests
```

`resolve` is the front door for the section skills and takes whatever you already had in front of you: a `DNN TNN §N` reference, a `<path> §N` pair, or a row pasted straight out of the generated plan. So `process todo section: | [ ] | D00 T01 §1 | ... |` is a complete instruction; nobody hand-translates a reference into a filename.

## Skills

| Skill | Use |
| ----- | --- |
| `add-todo` | Front door. Route new work to the right domain, file and section. |
| `create-todo` | Author a whole new TODO file, wire XREFs, update indexes. |
| `groom-plan` | Harden the tree for a weaker executor: sequence, drift, gaps, complete features. |
| `process-todo-section` | Fact-check the plan, fix drift, then ship one section. |
| `review-todo-section` | Quality gate after implementation; writes the stamp through `stamp`. |
| `process-todo-file` | Loose-end sweep and closure when every section is `[x]`. |
| `process-phase` | Attended phase runner: audit the phase, then ship or park it. |
| `process-plan` | Front door for `implementation-plan.md`; chains ready phases. |

When something needs doing, start at `add-todo`. Reaching for `create-todo` directly tends to produce a second TODO over an existing one.

## Rules for every file

- One line per paragraph and per list item in Markdown prose; no em dashes or en dashes in new text.
- Keep every section title (the `<Title>` in `## N. <Title>`), `Deliverable` cell, and index scope cell `<= 88` characters (`MAX_DELIVERABLE_LEN = 88`) so Markdown tables never wrap in the editor. Move detailed parenthetical symbol lists, file paths, CLI flags, and SPEC references into the section's context paragraph or checklist items.
- A defect noticed outside the current work is filed in `todo/findings.md` with `file:line`, not fixed on the side inside someone else's commit; scheduling it means writing a section through `add-todo`.
- Questions that need a person are not TODO rows without a Need: the section names `owner-decision` or `third-party` and records the answer before the Need is removed.
- Standing product decisions live in the foundation plan (D1 to D17). A section that effectively revises one records the correction there and here, dated, never silently.

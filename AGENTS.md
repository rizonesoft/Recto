## What is here

Recto is an open-source (`GPL-3.0-or-later`) PDF viewer, OCR tool and document converter for Windows: Recto's own native C++20 PDF engine (`recto-pdf`), C++20 concurrency, OCR and conversion runtime (`recto-core` and `recto-services`), and a WinUI 3 (Windows App SDK 2.4.0, C++/WinRT) app, distributed via Inno Setup (full installer and self-contained portable mode, plus an in-app Portable mode setting) and GitHub Releases, with optional MSIX packaging for the Microsoft Store. The repository holds the approved design, the foundation plan, the shipping graphics, the module scaffold, and the TODO execution plan that builds version 1 milestone by milestone (M0 to M6).

## The TODO system

`todo/` is the live execution plan; format spec: `todo/README.md`. Markdown is canonical. Nine domains map to the milestones: `00-workspace` (M0), `01-engine` (M1), `02-viewer` (M2), `03-text` (M3), `04-convert` (M4, M5), `05-organize` (M4), `06-quality`, `07-release` (M6), `99-manual` (operator only). Numbers are stable addresses: a new domain appends after the last.

Core mechanics: the Implementation Order table in each TODO file is the dependency graph; a row flips to `[x]` only through `python scripts/todo-graph.py stamp`, backed by a review receipt in `docs/reviews/`; `todo/implementation-plan.md` is regenerated by `plan --sync`, never ticked or edited by hand; cross-references (`§N`, `TNN §N`, `DNN TNN §N`) are bidirectional; every section declares Phase, Needs and Surface, carries a Build order with `Done when:` per step, and must be implementable with zero conversation context.

For TODO work, use the skill that owns the step: capture through `add-todo`, author a file through `create-todo`, build through `process-todo-section`, stamp through `review-todo-section` (running independent review rounds via `codex exec -m gpt-6-astra --ephemeral -`), close a file through `process-todo-file`, run a phase or the plan through `process-phase` or `process-plan`, harden the tree through `groom-plan`. The lifecycle is: capture, author, validate, record `Started:`, implement, run the section's gates, commit, review and stamp, sync the plan.

## Architecture rules that are not negotiable in passing

These come from foundation plan sections 3 and 4. A change that needs to break one records the correction in the plan first, dated, with the cost of reversing it.

- `recto-pdf` (`src/pdf`, compiled as C++20) is Recto's own native PDF 1.7 and 2.0 engine: zero MuPDF, zero C `setjmp`/`longjmp`, and zero PDF JavaScript execution by construction (D3, D9, D12). Every parser, stream filter, decryptor, digital signature verifier/signer (`crypt32.dll`/`bcrypt.dll`), content-stream interpreter, operator editor, form/annotation engine, redactor/sanitizer, PDF/A & PDF/UA & ZUGFeRD/Factur-X compliance engine, linearizer, and writer operation returns typed `PdfResult<T>` / `PdfError` values and bounds recursion and allocation against hostile inputs.
- One `DocumentActor` thread per open document owns its `recto::pdf::Document` instance and page object graph; immutable, reference-counted `DisplayList`s and `PageText` snapshots are the only page data that crosses threads to `RenderPool` workers; workers rasterize tiles in parallel with cooperative `CancelToken` abort; actors and workers join before `Runtime` shuts down. Files that touch this contract are `frozen: true` and carry a Freeze check per section.
- The UI thread never parses or renders PDFs and never blocks on an engine thread. Conversion, authoring, redaction, signing, optimization, and OCR jobs open their own `recto::pdf::Document` instance; they never share the viewer's.
- Built-in OCR (`Windows.Media.Ocr` + image preprocessing + vector-outlined-text OCR + searchable-PDF invisible-text layer synthesis) and native C++20 document converters (3-mode `PDF -> Word .docx/.rtf` Flowing/Exact/Continuous + orthogonal-line & grid table reconstruction, `PDF -> Excel .xlsx/.csv/.xml`, `PDF -> HTML5/Markdown/EPUB/LaTeX/SVG/XPS/Multipage TIFF/Animated GIF`, and built-in `Office/HTML/Markdown/XPS/SVG -> PDF` layout engine with optional Microsoft Office COM when installed) live in `recto-core` and `recto-services` with zero bundled external runtimes (D7, D10).
- Treat every PDF, Office, and HTML file as hostile: Office macros forced off during COM conversion, HTML scripts disabled, document links and portfolio attachments ask before opening, PDF launch and JavaScript actions never execute, and true redaction strips underlying content stream objects before drawing redaction overlays.
- Every file write is temp-file-then-replace in the destination folder. Organize and authoring operations always work on a copy; the open viewer document is never modified in place.

## Interface rules

- `design/SPEC.md` wins over any screenshot, mockup or memory. Colours come only from `design/tokens/RectoColors.xaml`; no control sets a hex value. Glyphs are Segoe Fluent Icons. Stock WinUI 3 controls first.
- One app shell, three layout presets (Focus default, Classic, Reading room) through settings and named slots: never three shells (D17).
- Every toolbar and menu command is reachable from the command box (Ctrl+K), every icon-only button carries an automation name and tooltip, and every control on a SPEC surface is accounted for as working or deferred to a named section before the section stamps.

## Working rules

- **Output discipline:** bound every command (filtered tests, `Select-Object -First`, field extraction). Keep full logs in ignored scratch (`R:\scratch` or `build/`).
- **Writes are serial:** one session owns the working tree. Check `git status` before building over unfamiliar work.
- **Fix at the owning layer:** a setting in its setting, behaviour in the code that produces it, a token in the token file. No output filters that hide a problem. Code changes end the report with a `Layer:` line.
- **Tests prove claims:** a section's Test checkpoint must be able to fail, and is quoted, not paraphrased, in its stamp. Engine and threading claims run under AddressSanitizer where the plan names it.
- **No em dashes** in authored prose. One line per paragraph and list item in Markdown. Keep every section heading (`## N. <Title>`), `Deliverable` cell, and index scope cell `<= 88` characters so Markdown tables never wrap.
- **Commits:** trunk-based `main`, concise imperative messages, the section ref in the body. Never amend a candidate under review, never bypass hooks, never force-push.
- **Credentials** never enter tracked files, arguments or logs. Store and signing material lives outside the repository.

## Unknowns and questions

Answer from source first: the foundation plan, the SPEC, the ISO 32000-1 / 32000-2 PDF specifications, ECMA-376 OpenXML, and Microsoft Learn for WinUI, Direct2D, DirectWrite, WIC, CNG and `Windows.Media.Ocr`. When an unanswered question would change implementation, take the industry-standard default, record that it is a default with its cost of changing, and carry on. Questions that truly need the owner become a section Need (`owner-decision`, `third-party`), not a stall.

Agent instructions for this repository. Claude Code loads this file through the `CLAUDE.md` import stub.

## What is here

Recto is an open-source (AGPL-3.0-or-later) PDF viewer and converter for Windows: a C17 MuPDF bridge, C++20 core and services, and a WinUI 3 (Windows App SDK 2.4.0, C++/WinRT) app, distributed as MSIX through the Microsoft Store. No application code exists yet: the repository holds the approved design, the foundation plan, the shipping graphics, and the TODO execution plan that builds version 1 milestone by milestone (M0 to M6).

## The TODO system

`todo/` is the live execution plan; format spec: `todo/README.md`. Markdown is canonical. Nine domains map to the milestones: `00-workspace` (M0), `01-engine` (M1), `02-viewer` (M2), `03-text` (M3), `04-convert` (M4, M5), `05-organize` (M4), `06-quality`, `07-release` (M6), `99-manual` (operator only). Numbers are stable addresses: a new domain appends after the last.

Core mechanics: the Implementation Order table in each TODO file is the dependency graph; a row flips to `[x]` only through `python scripts/todo-graph.py stamp`, backed by a review receipt in `docs/reviews/`; `todo/implementation-plan.md` is regenerated by `plan --sync`, never ticked or edited by hand; cross-references (`§N`, `TNN §N`, `DNN TNN §N`) are bidirectional; every section declares Phase, Needs and Surface, carries a Build order with `Done when:` per step, and must be implementable with zero conversation context. One section is one logical commit.

For TODO work, use the skill that owns the step: capture through `add-todo`, author a file through `create-todo`, build through `process-todo-section`, stamp through `review-todo-section`, close a file through `process-todo-file`, run a phase or the plan through `process-phase` or `process-plan`, harden the tree through `groom-plan`. The lifecycle is: capture, author, validate, record `Started:`, implement, run the section's gates, commit, review and stamp, sync the plan.

## Architecture rules that are not negotiable in passing

These come from foundation plan sections 3 and 4. A change that needs to break one records the correction in the plan first, dated, with the cost of reversing it.

- Only `recto-bridge` (`src/bridge`, compiled as C) includes MuPDF headers. Everything above it sees Recto's own types: no `setjmp` and `longjmp` across C++ frames, ever.
- One `fz_context` clone per thread; a document and its pages belong to their `DocumentActor` thread; display lists are the only page data that crosses threads; clones die before the base context. Files that touch this contract are `frozen: true` and carry a Freeze check per section.
- The UI thread never calls the bridge and never waits on an engine thread. Conversion jobs open their own document instance; they never share the viewer's.
- MuPDF is built with JavaScript disabled (D12), from a pinned submodule tag with Recto's own `mupdf-config.h` (D9): not vcpkg, not `mupdfcpp`.
- Treat every PDF and Office file as hostile: Office macros forced off during conversion, document links ask before opening, PDF launch actions never execute.
- Every file write is temp-file-then-replace in the destination folder. Organize operations always work on a copy; the open viewer document is never modified in place.

## Interface rules

- `design/SPEC.md` wins over any screenshot, mockup or memory. Colours come only from `design/tokens/RectoColors.xaml`; no control sets a hex value. Glyphs are Segoe Fluent Icons. Stock WinUI 3 controls first.
- One app shell, three layout presets (Focus default, Classic, Reading room) through settings and named slots: never three shells (D17).
- Every toolbar and menu command is reachable from the command box (Ctrl+K), every icon-only button carries an automation name and tooltip, and every control on a SPEC surface is accounted for as working or deferred to a named section before the section stamps.

## Working rules

- **Output discipline:** bound every command (filtered tests, `Select-Object -First`, field extraction). Keep full logs in ignored scratch (`R:\scratch` or `build/`).
- **Writes are serial:** one session owns the working tree. Check `git status` before building over unfamiliar work.
- **Fix at the owning layer:** a setting in its setting, behaviour in the code that produces it, a token in the token file. No output filters that hide a problem. Code changes end the report with a `Layer:` line.
- **Tests prove claims:** a section's Test checkpoint must be able to fail, and is quoted, not paraphrased, in its stamp. Engine and threading claims run under AddressSanitizer where the plan names it.
- **No em dashes** in authored prose. One line per paragraph and list item in Markdown.
- **Commits:** trunk-based `main`, concise imperative messages, the section ref in the body. Never amend a candidate under review, never bypass hooks, never force-push.
- **Credentials** never enter tracked files, arguments or logs. Store and signing material lives outside the repository.

## Unknowns and questions

Answer from source first: the foundation plan, the SPEC, MuPDF documentation and source, Microsoft Learn for WinUI. When an unanswered question would change implementation, take the industry-standard default, record that it is a default with its cost of changing, and carry on. Questions that truly need the owner become a section Need (`owner-decision`, `third-party`), not a stall.

## Validation

```powershell
python scripts/todo-graph.py validate        # graph integrity; any fault exits 2 with the reason
python scripts/todo-graph.py plan --check    # generated plan is current (CI runs this)
python scripts/todo-graph.py query ready     # dependency-safe work right now
python scripts/todo-graph.py query blocked   # sections waiting, and on what
python scripts/todo-graph.py query stats     # tree health
python scripts/todo-graph.py query deferred  # open and resolved deferrals
python -m unittest tests.scripts.test_todo_graph   # tooling tests, including the live tree
```

App build and test commands arrive with the M0 scaffold (`D00 T01 §3` owns the one-command build; both x64 and ARM64). Until then, sections name their build commands as the scaffold will provide them, and a claim that cannot run yet is recorded as not run, never narrated as passed.

Report only commands actually run, and distinguish static evidence, test output and review proof.
